# 项目深度评估（2026-04-17）

## 评估范围

- 代码：`src/` 主要功能模块（视图、标记、设置、加载器）
- 工程：`package.json`、`tsconfig.json`、`manifest.json`、`versions.json`
- 文档：`README.md`、`README-zh.md`、`CHANGELOG.md`

## 结论摘要（TL;DR）

当前项目已具备可用基础能力（构建可通过、模块拆分清晰），但存在 **发布治理、坐标一致性、文档可信度、类型安全** 四类高优先级问题。优先修复后可显著降低用户误用与后续维护成本。

## 关键问题（按优先级）

### P0：发布元数据不一致，存在发版阻塞风险

- `manifest.json` 与 `package.json` 版本均为 `1.0.0`，但 `versions.json` 只维护到 `0.1.6`。
- 影响：社区发布流程和版本映射校验可能失败，或造成安装兼容性判断错误。

### P0：右键菜单坐标顺序与声明规范不一致

- 代码和文档多处声明坐标格式为 `[longitude, latitude]`。
- 但右键菜单创建新笔记、复制坐标、设置中心点时使用了 `lat,lng` 顺序。
- 影响：用户通过右键操作生成的坐标可能与解析逻辑冲突，导致点位偏移/显示错误。

### P1：版本号硬编码多点重复，后续维护易漂移

- `main.ts` 与 `amap-view.ts` 分别硬编码 `1.0.0`。
- 影响：后续升级若未同步修改，UI/日志显示会与真实版本不一致。

### P1：文档存在事实冲突与重复内容

- `CHANGELOG.md` 声称“自动 WGS-84→GCJ-02 转换”，但当前实现强调仅支持 GCJ-02输入。
- `README.md` 中申请 Key 的步骤出现重复段落。
- `README-zh.md` 部分示例坐标顺序与 `[经度, 纬度]` 约定相反。
- 影响：新用户上手失败率上升，问题排查成本增加。

### P1：类型与输入约束仍有欠缺

- `env-loader.ts` 使用 `vault: any`，降低类型保护。
- `tsconfig.json` 未开启完整 `strict`；当前只启用了部分严格项。
- 影响：重构时更容易引入运行时错误。

### P2：交互与可维护性细节可优化

- `markers.ts` 同一个 marker 注册了两次 `mouseover` 监听（弹窗与 hover-link 预览），可合并简化。
- `amap-view.ts` 的 map type 视图选项为自由文本，输入非法值时缺少显式约束提示。
- 影响：行为复杂度增加，可读性和可测试性下降。

## 建议的修复路线图

### 第一阶段（1~2 天）：风险止血

1. 同步版本治理：对齐 `manifest.json`、`package.json`、`versions.json`。
2. 统一坐标顺序：右键菜单所有输出改为 `[lng, lat]`；增加回归用例。
3. 删除版本硬编码：从构建注入或单一源读取版本号。

### 第二阶段（2~4 天）：工程质量提升

1. 修正文档冲突（坐标顺序、WGS-84 描述、重复步骤）。
2. 收紧类型：为 Vault 引入准确类型声明，减少 `any`。
3. 评估开启 `strict: true` 的改造清单并分批落地。

### 第三阶段（持续）：可维护性优化

1. 合并重复事件监听，补充注释说明交互链路。
2. 为 map type 等配置项增加枚举验证与容错回退。
3. 增加最小化自动化校验（至少 CI 执行 `npm run build` + 文档一致性检查）。

## 风险矩阵（简版）

- **高影响 / 高概率**：版本映射不一致、坐标顺序反转。
- **高影响 / 中概率**：文档与实现冲突导致误配。
- **中影响 / 中概率**：硬编码版本漂移、类型约束不足。
- **中影响 / 低概率**：重复事件监听带来的维护复杂度。
